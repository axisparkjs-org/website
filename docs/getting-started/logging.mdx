# Logging

Logging is an essential part of any application, as it allows you to track the behavior of your application and diagnose issues when they arise. In AxiSpark.js, you can use the built-in logging system to log messages at different levels (e.g., info, warn, error) and configure the logging output to suit your needs.

## Logging Levels

The logging system in AxiSpark.js supports the following levels, ordered from lowest to highest priority:

        <tr>

## Structured metadata

Every level method accepts an optional `metadata` object with structured data about the entry. `error` and `fatal` receive it after the error, so the current calls keep working:

```ts
await logger.info('Request completed', { method: 'GET', path: '/users', status: 200, durationMs: 12 });
await logger.error('Payment failed', error, { orderId });
await logger.fatal('Database unreachable', undefined, { host: 'db.internal' });
```

Prefer metadata to values inside the message string: the `JsonFormatter` writes it as a `metadata` field, so log processors can filter the entries by its values.

### Metadata bound to child loggers

`child(scope, metadata?)` creates a logger with an additional scope and, optionally, metadata that is added to every entry it writes. Nested child loggers merge their metadata with the metadata of their parents, and the metadata passed to a level method overrides the bound values with the same key:

```ts
const requestLogger = logger.child('HttpPlugin', { requestId });

await requestLogger.info('Route matched', { route: '/users/:id' });
// metadata: { requestId, route: '/users/:id' }
```

The parent logger is not modified, so its entries do not include the metadata of its children.

## Logging Formatters

AxiSpark.js allows you to configure the logging output format using formatters. Formatters define how log messages are structured and displayed. You can use built-in formatters or create your own custom formatters to suit your needs.

### Built-in Formatters

Here are the built-in formatters available in AxiSpark.js. In total are 5 built-in formatters, which you can use to format your log messages. You can choose the formatter that best fits your application's logging requirements:

    <thead>
        <tr>
            <th>Formatter</th>
            <th>Description</th>
        </tr>
    </thead>
    <tbody>
        <tr>
            <td>`SimpleFormatter`</td>
            <td>Outputs log messages in plain text format, which is suitable for console output and simple logging needs. The metadata is printed as JSON after the message.</td>
        </tr>
        <tr>
            <td>`PrettyFormatter`</td>
            <td>Outputs log messages in a human-readable format with colors and indentation, which is suitable for console output and debugging.</td>
        </tr>
        <tr>
            <td>`JsonFormatter`</td>
            <td>Outputs log messages in JSON format, which is suitable for structured logging and integration with log management systems.</td>
        </tr>
        <tr>
            <td>`XmlFormatter`</td>
            <td>Outputs log messages in XML format, which is suitable for structured logging and integration with log management systems.</td>
        </tr>
        <tr>

            <td>Allows you to define your own custom formatter by providing a template string with the `{timestamp}`, `{level}`, `{message}`, `{scopes}`, `{metadata}` and `{error}` placeholders.</td>
        </tr>
    </tbody>
</table>

### Create your own formatter

In order to create your own custom formatter, you can extend the `LogFormatter` class and implement the `format` method. The `format` method takes a log message object as input and returns a formatted string. Here's an example of how to create a custom formatter that outputs log messages in a specific format:

```ts title="custom-formatter.ts"
import { LogEntry, LogFormatter } from '@axisparkjs/logger';

export class CustomFormatter implements LogFormatter {
    format(entry: LogEntry): string {
        ...

        return `Custom formatted message`;
    }
}
```

## Logging Transporters

Transporters are responsible for sending log messages to their final destination, such as a file, console, or external logging service. AxiSpark.js provides several built-in transporters that you can use to send log messages to different destinations.

### Built-in Transporters

    <thead>
        <tr>
            <th>Transporter</th>
            <th>Description</th>
        </tr>
    </thead>

### Sending the HTTP logs in batches

By default, `HttpTransport` makes one request per message. Set `batch` to send them together, as a JSON array, when `size` messages are waiting or after `interval` milliseconds:

```ts
new HttpTransport({
    url: 'https://logs.example.com/ingest',
    minLevel: LogLevel.Info,
    formatter: new JsonFormatter(),
    batch: { size: 100, interval: 1000 } // `batch: true` uses these defaults.
});
```

- The call to the logger does not wait for the request, so logging does not add the latency of the endpoint to your code.
- `app.destroy()` calls `logger.flush()`, which sends the waiting messages and waits for the requests. Call it before exiting the process in other ways.
- The endpoint receives an array of entries instead of one entry, so enable the option only when it accepts arrays.
- A failed batch is reported to `onError` once for each of its messages, or on `process.stderr` at most once a minute. `failOnError` does not apply, because nobody is waiting for the request.

### When a transporter fails

A transporter that fails, for example because its endpoint is down or the disk is full, never breaks the code that logs: `logger.info()`, `logger.error()` and the other level methods do not reject because of a transporter, and the other transporters still receive the entry.

The failure is written to `process.stderr` at most once per transporter every minute, so it is visible without flooding the output. To handle it in another way, pass the `onError` option to the transporter:

```ts
new HttpTransport({
    url: 'https://logs.example.com/ingest',
    formatter: new JsonFormatter(),
    minLevel: LogLevel.Info,
    timeout: 2000,
    onError: (error, entry) => metrics.increment('log_delivery_failures')
});
```

Some logs must stop the operation when they can not be written, such as audit logs. Set `failOnError: true` on their transporter: a failure of that transporter rejects the call to the logger, after the entry has been sent to the other transporters.

### Create your own transporter

As well as formatters, you can create your own custom transporter by extending the `LogTransport` class and implementing the `write` method. The `write` method takes a log message object as input and sends it to the desired destination. Here's an example of how to create a custom transporter that sends log messages to a specific destination:

```ts title="custom-transporter.ts"
import { LogEntry, LogTransport } from '@axisparkjs/logger';

export class CustomTransport extends LogTransport {
    async write(entry: LogEntry): Promise<void> {
        if (entry.level < this.config.minLevel) return;

        console.log(this.config.formatter.format(entry));
    }
}
```

## Configuring the application logger

When you create an AxiSpark.js application, you can configure the logger by providing a configuration object to the `AxiSparkFactory` method. The configuration object allows you to specify the logging level, formatter, and transporter for the application logger. 


```ts title="app.ts"
AxiSparkFactory.create({
    logTransports: [
        new ConsoleTransport({
            minLevel: LogLevel.Info,
            formatter: new SimpleFormatter()
        })
    ]
    ...
});
```

> You can add multiple transporters to the `logTransports` array, allowing you to send log messages to multiple destinations simultaneously. Each transporter can have its own configuration, including the minimum logging level and formatter.

### Default transport

When `logTransports` is not set, the application uses a single `ConsoleTransport` with the `LogLevel.Trace` minimum level and the `SimpleFormatter`, which is equivalent to:

```ts title="app.ts"
AxiSparkFactory.create({
    logTransports: [new ConsoleTransport({ minLevel: LogLevel.Trace, formatter: new SimpleFormatter() })]
});
```

Every entry, including the banner, is written to the standard output. Set `logTransports` to change the level, the format or the destination of the logs.

### Writing logs to stderr

Some applications must keep the standard output free, because it carries data that other programs read. The main case is the [MCP stdio transport](../mcp-plugin/installation#4-use-the-stdio-transport-optional), where the standard output carries the protocol messages and any other output breaks the connection. Write the logs to `stderr` with a `StreamTransport` over `process.stderr`:

```ts title="app.ts"
import { AxiSparkFactory } from '@axisparkjs/core';
import { LogLevel, SimpleFormatter, StreamTransport } from '@axisparkjs/logger';

export const app = AxiSparkFactory.create({
    name: 'Users App',
    basePath: __dirname,
    logTransports: [new StreamTransport({ stream: process.stderr, minLevel: LogLevel.Info, formatter: new SimpleFormatter() })]
});
```

Do not use a `ConsoleTransport` in these applications, because it writes to the standard output. The framework does not change the transports for you: the configuration of `logTransports` is always the one you provide.
