# Timeouts

The engine also supports timeouts for an execution context. This is, when a execution (request) takes longer than a specified time, it will be automatically canceled and an error will be thrown. This is useful to prevent long-running executions from blocking the system.

Each transport has its own timeout configuration, enabling you to set different timeouts for different transports. The timeout can be configured in the transport options when creating the transport instance. Also, when using the `@Timeout()` decorator, you can specify a timeout for a specific step or method. This allows you to have fine-grained control over the timeout behavior of your engine steps. The `@NoTimeout()` decorator can be used to disable the timeout for a specific step or method, even if the transport has a timeout configured.

The timeout of a handler is resolved in this order, and the first one defined wins:

1. The `@Timeout()` or `@NoTimeout()` of the method.
2. The `@Timeout()` or `@NoTimeout()` of its class.
3. The default timeout of the transport.

So `@NoTimeout()` on a method disables a `@Timeout()` of its class and the default timeout of the transport, and `@NoTimeout()` on a class disables the timeout of all its handlers, unless a method has its own `@Timeout()`. A handler without a timeout runs to the end, whatever the default timeout of the transport.

The time of `@Timeout(time)` must be a number of milliseconds greater than `0`. `@Timeout(0)` or a negative time throws an error when the decorator is applied, so the mistake is visible at startup. Use `@NoTimeout()` to disable the timeout.

The engine also provides a default timeout for all transports (5000ms) in case you enable the timeout feature but do not specify a timeout for a specific transport or step.

> Important, the `@Timeout()` and `@NoTimeout()` decorators will only work if the transport has enabled the timeout feature. The WebSocket and MCP plugins always handle the `@Timeout()` of their handlers, even without a default timeout.

When an execution times out on a transport that has no timeout handler registered, the engine throws an `ExecutionTimeoutError` (`Execution timed out after <time>ms`). The error filters of the transport handle it like any other error, so a timeout never ends with an empty response.

The timeout covers the execution of the handler, not the transfer of the response. A handler that returns `HttpResults.Stream()` or `HttpResults.File()` ends when it returns the result, so a long download is not stopped by the timeout.

## Example of Timeouts in Http Transport

```ts title="app.ts"
app.use(
    HttpPlugin,
    HttpPluginOptionsFactory.create({
        ...
        timeout: true,
        timeoutOptions: {
            time: 3000, // 3 seconds in case no decorator is used. 5 seconds is the default timeout for all transports.
            message: (time: number) => `Request timeout after ${time} ms`
        }
        ...
    })
);
```

```ts title="example-controller.ts"
@Timeout(2000)
@Controller('timeouts')
export class TimeoutController {
    @Get()
    async exampleTimeout() {...}

    @Get('no-timeout')
    @NoTimeout()
    async exampleNoTimeout() {...}

    @Timeout(10) // 10 milliseconds
    @Get('throw-timeout')
    async exampleThrowTimeout() {...}
}

@NoTimeout()
@Controller('reports')
export class ReportController {
    @Get()
    async generateReport() {...} // No timeout

    @Get('summary')
    @Timeout(1000) // The method timeout takes precedence over the @NoTimeout() of the class
    async generateSummary() {...}
}
```
